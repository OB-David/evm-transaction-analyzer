# 时序图计算加速方案

## 目标

当前时序图在渲染前同步查询 4byte，函数名解析会阻塞 Sequence 和后续 CFG。优化分两阶段推进，每阶段都用同一批交易比较总耗时、函数解析耗时和缓存命中率。

## 第一阶段：本地函数签名库

- 建立本地 SQLite，保存 4byte 的全部 `selector → 完整 signature、函数名、优先级`；来源只在 metadata 中保存一次，运行时只查本地，不再逐次请求 4byte。
- 全量同步使用临时库和断点续传；只有本地记录数与稳定的 API 快照一致时才原子发布，之后可定期重跑刷新。
- 体量实测：4byte 官方 API 共 **1,179,049 条**函数签名、**1,178,638 个**唯一 selector；删除逐行重复的来源和未使用的创建时间后，SQLite 由 **279.3 MiB** 降至 **98.8 MiB**。本项目现有 44 笔分析只涉及约 **218 个有效唯一 selector**。
- 实测：同一笔真实交易的 PUML 构建由 **2466 ms** 降至约 **1.8 ms**；单 selector 本地查询平均约 **0.016 ms**，第一阶段已达到目标。

## 第二阶段：函数名退出关键路径

若第一阶段仍不够快，图构建阶段只使用 4-byte selector（如 `0xa9059cbb`），立即生成并发布 SVG；函数名在后台查询本地库或补充数据，完成后再更新前端标签和候选详情。

这样即使数据库未命中或更新失败，也不会阻塞图生成；selector 始终保留，函数名仅作为可延迟、可失败的辅助信息。

## 决策逻辑

```text
先做本地库并实测
  ├─ 已满足延迟目标：保留同步本地解析
  └─ 仍不满足：先渲染 selector，后台补函数名
```

体量参考：`4byte.directory/api/v1/signatures/`（实时 count）和 `ethereum-lists/4bytes` 官方签名数据集。
