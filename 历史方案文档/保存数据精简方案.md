# 交易分析数据精简方案

## 1. 结论

当前问题不是单纯的文件数量过多，而是：

1. 长期保存了完整执行状态和渲染中间文件；
2. 同一份语义在 trace、block information、DOT、映射 JSON 中反复出现；
3. 真正可复用的调用树、资产流和 CFG 语义反而没有形成稳定的数据模型；
4. 一些计算结果只是展示提示，却在每次分析中默认计算并单独保存。

本方案的核心决策是：

- 默认不保存 `trace.json`；trace 只在单次分析进程中以内存或临时数据存在，所有核心结果计算完成后立即释放。
- 保存足以重新展示、重新渲染和重新执行资产流检测的结构化语义数据。
- SVG 不落盘；需要时从 DOT/结构化数据渲染后直接返回。
- 停止生成旧时序图；保存真正的 `call_tree.json`。
- Folded/Plain CFG 保存 DOT 图源，SVG 由后端按请求生成且不写入结果目录。
- 完整 trace 仅在显式审计/调试模式下压缩归档。

### 1.1 当前实施状态

第一阶段基础改造已开始，当前代码已经完成：

- 新分析写入 `call_tree.json`，其中包含显式 `parent_call_id/depth/from_address/to_address`；
- 前端只读取最新的 `call_tree.json`，不再兼容旧调用树映射；
- 分析管线停止生成 `trace_sequence.puml` 和 `trace_sequence.svg`；
- 默认停止写入 `trace.json`；
- Plain block LLM 改读 `plain_semantics.json.gz`，旧目录仍可回退读取 `trace.json`；
- Folded/Plain CFG 停止保存 SVG，改为保存 DOT 图源并由 API 按需渲染；
- `TFG_link_FCFG.json` 与 `TFG_link_PCFG.json` 合并为版本化的 `link.json`；
- CFG 拓扑和 information 分阶段发布：两张 DOT 就绪后前端立即展示，详情继续在后台计算；
- 分析阶段通过子进程 stdout 和服务端内存进度传递，不写 `analysis_status.json`；
- Plain block 指令生成由全 trace 重扫改为 step range 直接切片；
- 取消未被消费的 `original_cfg` 深拷贝；
- timing 改为分析结束时统一写入，不再每个 phase 扫描目录和重写文件。

目标交易实测：

- 新 `call_tree.json` 约 `11.7 KB`，生成约 `0.01 秒`；
- 新 `plain_semantics.json.gz` 约 `397 KB`，而原 `trace.json` 为 `26.8 MB`；
- `plain_semantics` 保留当前 LLM 使用的局部 stack/memory 语义，不包含完整 trace 容器。

两笔实测中，一笔总耗时约 `6.22 秒`、information 合计约 `2.31 秒`；交易 `df5ad6...f16ea` 改造后总耗时约 `9.51 秒`，两张 CFG DOT 仅约 `20 ms`，随后 Folded/Plain information 合计约 `4.91 秒`。因此分阶段展示可分别提前约 `2.3–4.9 秒`看到 CFG 拓扑。

尚未实施的重点包括统一 `asset_flow.json/entities.json`、storage tracer 精简和跨交易静态分析缓存。

## 2. 当前数据与耗时证据

### 2.1 存储占用

当前 `data_base/analysis` 中：

- 全部分析文件约 `3.636 GB`；
- 35 个 `trace.json` 合计约 `3.503 GB`，占总量约 `96.4%`；
- 目标交易的 `trace.json` 为 `26.8 MB`；
- 同一文件压缩为 gzip 后约 `428 KB`，说明主要内容是重复的 stack/memory 快照；
- 36 份 folded/plain CFG SVG 合计约 `22.6 MB`；
- 36 份 folded/plain CFG DOT 合计约 `7.45 MB`。

因此，第一优先级必须是取消默认 trace 落盘，而不是优先删除几十 KB 的小 JSON。

### 2.2 渲染与生成耗时

22 笔已有 `analysis_timing.json` 的统计如下：

| 阶段 | 平均 | P50 | P95 | 最大值 |
|---|---:|---:|---:|---:|
| Folded CFG SVG 布局 | 171 ms | 46 ms | 594 ms | 635 ms |
| Plain CFG SVG 布局 | 73 ms | 52 ms | 142 ms | 164 ms |
| 旧时序图 SVG 布局 | 1,148 ms | 1,129 ms | 1,237 ms | 1,916 ms |
| Plain CFG 元数据生成 | 1,233 ms | 464 ms | 1,776 ms | 12,853 ms |
| 完整 trace JSON 写入 | 763 ms | 519 ms | 1,255 ms | 2,999 ms |

对目标交易直接运行 Graphviz 五次：

- `folded_cfg.dot -> SVG`：每次约 `0.04–0.05 秒`；
- `plain_cfg.dot -> SVG`：每次约 `0.05 秒`。

结论：CFG 图片重新布局通常不慢。真正不值得保留和计算的是 PlantUML 时序图；Plain 模式的主要瓶颈也不是 SVG，而是当前低效的元数据构造。

## 3. 默认不保存 trace 如何继续完成计算

“不保存 trace”不等于“不获取 trace”。默认流程应改为：

```text
RPC 获取 raw trace
  -> 在分析进程内标准化/流式处理
  -> 构建调用树
  -> 构建执行 CFG、Folded CFG、Plain CFG 语义模型
  -> 提取 ETH/ERC-20 原始资产事件
  -> 配对资产流、保留未配对 mint/burn
  -> 检测候选闭环、计算精确净变化
  -> 写入精简后的结构化产物
  -> 保存 CFG DOT 图源；SVG 请求时生成但不落盘
  -> 释放 trace，不写 trace.json
```

当前管线本来就在一个 `main_api.py` 子进程中完成上述计算，因此第一阶段只要取消 `write_full_trace_json`，不会影响当次 AFG、调用树、Folded CFG、Plain CFG、余额变化或候选闭环计算。

### 3.1 必须提前替代的 trace 消费者

目前分析完成后仍读取 `trace.json` 的主要功能是 Plain CFG 的 LLM block analysis。取消 trace 落盘前必须二选一：

方案 A，推荐：分析过程中生成紧凑的 `plain_semantics.json.gz`。

- 按 Plain block 保存 LLM 真正使用的 opcode、相关 stack operands、必要 memory slice、地址、step 和 gas；
- 不保存每一步完整 stack 和完整 memory；
- 使用当前 `_build_opcode_step_context()` 的归一化结果，而不是保存其输入；
- 文件按 block 索引，后续 LLM 只读取目标 block 及相邻 block。

方案 B：用户首次请求 LLM 分析时重新向 RPC 获取 trace。

- 本地存储最少；
- 但依赖历史节点可用性，延迟高，并会重复支付 RPC 成本；
- 只适合作为 `plain_semantics` 缺失时的回退。

默认采用方案 A，方案 B 作为兼容回退。

### 3.2 不保存 trace 后的能力边界

精简产物应支持：

- 重新渲染 AFG、调用树、Folded CFG 和 Plain CFG；
- 重新计算地址/资产净变化；
- 在保留原始资产事件的前提下重新运行 transfer pairing 和候选闭环检测；
- 按 PC/step 追溯每条资产边和调用；
- 继续进行 Plain block LLM 分析。

但如果未来修改的是“如何从 SLOAD/SSTORE/stack/memory 中识别资产变化”的底层提取算法，旧精简产物无法代替完整 trace。此时应重新从 RPC 获取 trace，或使用显式开启的审计归档。

### 3.3 可选审计模式

提供配置，例如：

```text
TRACE_RETENTION=none        # 默认，不落盘
TRACE_RETENTION=compressed  # 保存 trace.json.zst
TRACE_RETENTION=debug       # 临时保存可读 JSON，并设置 TTL
```

即使开启归档，也不再保存缩进后的 `trace.json`，优先使用 zstd/gzip 压缩。

## 4. 渲染图片是否保存

### 4.1 总体原则

- JSON/结构化数据是事实来源；
- SVG 只存在于 HTTP 响应和浏览器 DOM，不进入分析目录；
- 当前迁移阶段以 DOT 作为 CFG 可重建图源；
- 后续引入完整 CFG JSON 后，可以再取消 DOT 持久化；
- 服务端不维护磁盘 SVG 缓存，避免渲染版本和主题变更产生脏缓存。

### 4.2 各视图决策

| 视图 | 语义数据 | SVG 策略 | DOT 策略 | 原因 |
|---|---|---|---|---|
| 调用树 | 保存 `call_tree.json` | 不保存、不由后端生成 | 不需要 | 前端已能直接用 Vue/SVG 绘制；旧 PlantUML 平均浪费约 1.15 秒 |
| AFG | 保存 `asset_flow.json` | 默认不保存 | 迁移期保留 `asset_flow.dot`，最终不保存 | 图通常很小，交互需要结构化边数据，客户端渲染成本低 |
| Folded CFG | 当前保存 `folded_cfg.dot`，后续升级为 JSON | 不保存，访问时返回 | 持久化 | 保证服务重启后不重新分析交易也能渲染 |
| Plain CFG | 当前保存 `plain_cfg.dot`，后续升级为 JSON | 不保存，访问时返回 | 持久化 | Plain 模式按需布局，不阻塞分析阶段 |

### 4.3 当前渲染策略

1. 分析阶段只生成 `folded_cfg.dot` 和 `plain_cfg.dot`，不执行 Graphviz SVG 布局。
2. 前端访问 CFG 时调用渲染 API，后端通过 `dot -Tsvg` 将结果直接写入 HTTP 响应。
3. SVG 不写入结果目录，重复访问会重新布局；历史实测通常约 `0.05 秒`。
4. 若未来并发渲染成为瓶颈，应优先增加有界内存缓存或 HTTP 缓存，而不是恢复磁盘 SVG 产物。

## 5. 新的持久化产物

每笔交易建议从当前约 22 个文件收敛为：

```text
manifest.json
entities.json
asset_flow.json
call_tree.json
folded_cfg.json
plain_cfg.json
link.json               # 同时包含 folded/plain AFG→CFG 关联
plain_semantics.json.gz
trace.json.zst          # 仅 TRACE_RETENTION=compressed/debug 时存在
```

### 5.1 `manifest.json`

保存：

- `artifact_schema_version`；
- tx hash、chain ID、block number；
- 分析状态与失败原因；
- detector/version、renderer/version；
- 各语义产物是否完整；
- 分析时间摘要。

不保存：

- 绝对 `result_dir`；
- 每个阶段反复更新的 artifact size；
- 可通过目录枚举得到的完整文件列表。

不生成 `analysis_status.json`。分析子进程通过 stdout 发布 `afg/sequence/folded_cfg/plain_cfg/folded_info/complete` 阶段事件，服务端只在内存中维护运行进度，前端通过 progress API 获取；完成状态由最终必需产物集合确认。`analysis_timing.json` 改为开发模式或集中 metrics。

### 5.2 `entities.json`

按规范化地址建立唯一实体注册表：

```json
{
  "schema_version": 1,
  "entities": {
    "0xc02a...": {
      "kind": "erc20",
      "name": "Wrapped Ether",
      "symbol": "WETH",
      "decimals": 18,
      "color": "#..."
    }
  }
}
```

它替代以下重复数据：

- `legend.json`；
- trace 顶层的 `contracts_addresses`、`users_addresses`；
- `erc20_token_map`；
- `full_address_name_map`；
- 各事件反复保存的 `token_name`。

资产身份使用 `(chain_id, token_address)`，symbol 仅作为展示信息。

### 5.3 `asset_flow.json`

统一保存：

- 原始 ETH/ERC-20 资产事件；
- paired transfer 和未配对 mint/burn；
- 节点与稳定 edge ID；
- raw amount、decimals、格式化展示值；
- 每条边的 PC/step evidence；
- Folded/Plain CFG 映射；
- 地址/资产精确净变化；
- candidate cycle 检测结果及 detector version。

示例事件：

```json
{
  "event_id": "event_7",
  "kind": "erc20_balance_delta",
  "asset_id": "1:0x72e4...",
  "account": "0x7c1c...",
  "raw_delta": "-1117465072043",
  "evidence": [
    {"role": "sload", "step": 1277, "pc": "0x1238"},
    {"role": "sstore", "step": 1374, "pc": "0x125b"}
  ]
}
```

每条 flow edge 直接包含：

```json
{
  "edge_id": "flow_2",
  "order": 2,
  "from": "0x...",
  "to": "0x...",
  "asset_id": "1:0x...",
  "raw_amount": "1117465072043",
  "event_ids": ["event_7", "event_8"],
  "cfg": {
    "folded": {"block_ids": [8], "status": "complete"},
    "plain": {"block_ids": [63], "status": "complete"}
  }
}
```

由此删除：

- `balance_and_eth_changes.json`；
- `arbitrage.json`；
- `address_balances.json`；
- `TFG_link_FCFG.json`；
- `TFG_link_PCFG.json`。

其中 `is_arbitrage` 改为 `has_candidate_cycle`；`arb_edge_orders` 由 ordered cycles 推导，不单独保存。净变化保存 raw integer，不使用 float，也不以 token symbol 作为唯一键。

### 5.4 `call_tree.json`

后端已经构造了层级调用树，不应再压平后让前端按区间重新推断。每个调用保存：

```json
{
  "call_id": 3,
  "parent_call_id": 1,
  "depth": 2,
  "from_address": "0x...",
  "to_address": "0x...",
  "entry_op": "CALL",
  "exit_op": "RETURN",
  "entry_step": 1867,
  "exit_step": 12829,
  "selector": "0x10d1e85c",
  "calldata_slices": ["0x10d1e85c", "0x..."],
  "probable_text_signatures": ["uniswapV2Call()"]
}
```

删除可推导字段：

- `total_calls`，由数组长度得到；
- `from_name/to_name`，通过 `entities.json` 连接；
- 前端重新推断的 parent/depth/descendant count。

文件替代：

- `trace_sequence_calldata_mapping.json`；
- `trace_sequence.puml`；
- `trace_sequence.svg`。

### 5.5 `folded_cfg.json`

每个 Folded block 只保存：

- block ID、address；
- 全部 `step_ranges`；
- gas；
- folded membership 或必要映射；
- event IDs；
- 用于节点展示的少量 opcode summary。

删除：

- 每个节点重复的 `schema_version`；
- map key 与内部 `block_id` 的双重 ID；
- `blocks_number`，由 membership 长度推导；
- 全量 instructions；
- 完整 actions 副本；
- 旧版 `start_pc/end_pc`。

CFG edge 自带 `edge_id/source/target/type/step`，SVG 中写入相同的 `data-edge-id/data-step`。由此删除 `edge_id-step.json`。

### 5.6 `plain_cfg.json`

Plain CFG 是删除 trace 后唯一需要长期保存的指令级证据。保留：

- block ID、address；
- `start_step/end_step`；
- gas；
- event IDs；
- 结构化 PC/opcode 指令；
- CFG edges。

当前指令是 JSON 中的 Python 字符串：

```json
"{'pc': '0x1', 'opcode': 'CALLDATALOAD'}"
```

应改为紧凑结构：

```json
["0x1", "CALLDATALOAD"]
```

不再保存：

- 重复 `block_id`；
- `blocks_number`；
- 可由首尾指令得到的 `start_pc/end_pc`；
- 完整 action payload，改用 event IDs。

## 7. 可以直接取消或减少的计算

### 7.1 立即取消

- PlantUML PUML 生成和 Java SVG 布局；
- 完整 `trace.json` 的 pretty JSON 序列化和写盘；
- SLOAD/SSTORE storage delta 的 tracer 采集、Python 合并和标准 step 存储；
- 两套 swap JSON 的写盘、重新读取、`ast.literal_eval` 和全指令扫描；
- 未被入口消费的 `original_cfg = deepcopy(cfg)`；
- 已不再使用的 `original_cfg/folded_node_map/table` 返回值；
- 每个 timing phase 都扫描目录并重写 timing JSON。

### 7.2 memory/stack 精简

不能简单关闭全部 stack/memory，因为资产识别和 calldata 仍需要部分值。应改为：

- memory 在处理过程中维护当前状态，但只提取 CALL calldata、KECCAK mapping 输入和 LLM 需要的局部 slice；
- 不为 14,000 多个 step 分别保存完整 memory 快照；
- stack 默认不落盘；
- 后续可使用 compact custom tracer，仅输出 CALL、SLOAD、SSTORE、KECCAK 等 opcode 的必要 operands；
- PC/opcode/depth/gas/address 保留为瞬时执行信息，并投影到 call、block、edge、event 数据。

### 7.3 RPC 和跨交易缓存

- 同一交易对象当前被多个函数重复查询，应在入口获取一次后传递；
- ERC-20 识别已经查询 `name/decimals`，后续不应再次查询 decimals 和 NFT 接口；
- bytecode 按 `chain_id + address + block/codehash` 缓存；
- basic blocks 按 `bytecode_hash + EVM version` 跨交易缓存；
- token metadata 按 `chain_id + token_address + block` 缓存；
- DELEGATECALL 关系先对 steps 建索引，不要对每个 token 再扫描一遍完整 trace。

### 7.4 Plain CFG 元数据复杂度

当前实现对每个 Plain block 都遍历全部 steps，复杂度接近 `O(blocks × steps)`。应改为：

```python
matched_steps = steps[start_step:end_step + 1]
```

或在一次线性扫描中按 block 分桶。该优化比删除 Plain SVG 更重要，因为历史最坏耗时达到约 12.85 秒。

## 8. 分阶段实施顺序

### 第一阶段：低风险立即收益

1. 停止 PlantUML 和旧时序 SVG；拆出独立 `call_tree.json` writer。
2. 停止写 `trace.json`，同时加入 `plain_semantics.json.gz`。
3. 停止保存 CFG SVG，持久化 CFG DOT 并提供按需渲染 API。
4. 删除 `original_cfg` 无用深拷贝和无用返回值。
5. 修复 Plain block 指令区间构造的 `O(blocks × steps)`。
6. timing 只在结束时写一次。
7. 两份 `TFG_link_*` 合并为一个版本化 `link.json`。

### 第二阶段：统一语义契约

1. 引入 `manifest.json` 和 schema version。
2. 引入 `entities.json`。
3. 引入统一 `asset_flow.json`，迁移五个资产相关 JSON。
4. 引入 `folded_cfg.json/plain_cfg.json`，把 edge-step 和 actions 改成内部引用。
5. 前后端同时迁移类型、loader 和缺失状态处理。

### 第三阶段：按需渲染和流式 trace

1. 已完成：Folded/Plain DOT 先发布，information 后台继续生成，前端分阶段启用详情交互。
2. 监控按需 SVG 渲染延迟；必要时增加有界内存或 HTTP 缓存。
3. CFG JSON 完整包含节点和边后，评估取消 DOT 持久化。
4. memory 改为流式局部 slice，不再构造每步完整快照。
5. 评估 compact custom tracer，进一步取消完整 stack 返回。
6. 增加跨交易 bytecode/basic-block/token-metadata 缓存。

### 第四阶段：旧数据处理

- 前端不读取旧契约，旧目录必须重新分析或离线迁移后才能展示；
- 不设置兼容 reader，避免旧字段被静默解释成最新语义；
- 删除旧文件前先验证新产物能完整重建 AFG、调用树和两种 CFG。

## 9. 验收标准

### 存储

- 默认分析目录中不存在 `trace.json`、PUML 和任何 SVG；
- 当前迁移阶段保留 Folded/Plain CFG DOT，确保 SVG 可按需重建；
- 完整 trace 仅在显式配置下以压缩形式存在；
- 新产物不重复保存 token name、完整 actions、Folded instructions 和 edge 映射；
- SVG 可以从持久化 DOT 重新生成，且渲染过程不写盘。

### 功能

- 不保存 trace 时仍能生成 AFG、调用树、Folded CFG 和 Plain CFG；
- CFG DOT 就绪后无需等待 information 即可展示拓扑；information 未完成时详情和 LLM 明确显示为计算中；
- 服务重启后无需重新 RPC trace 即可重新展示和重新渲染四个视图；
- Plain block LLM 不依赖 `trace.json`；
- AFG edge 能同时联动 Folded/Plain CFG；
- unmatched ERC-20、mint/burn、ETH/WETH 镜像证据不丢失；
- candidate cycle 与 profitable arbitrage 明确区分；
- 缺失缓存、缺失语义数据和确定的“无候选闭环”具有不同状态。

### 性能

- 去除约 0.5–3 秒的 trace JSON 写盘；
- 去除约 1.1 秒的 PlantUML 布局；
- Plain 元数据生成由 `O(blocks × steps)` 降至 `O(steps)`；
- CFG SVG 布局从分析阶段移到实际访问阶段；
- 常规 CFG 按需渲染通常在百毫秒级完成。
