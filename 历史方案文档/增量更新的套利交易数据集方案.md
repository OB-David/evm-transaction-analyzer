# 历史 Arbitrage 本地同步方案

## 核心方案

只支持 Ethereum Mainnet。Dune 的 arbitrage 结果存到本地 SQLite，Block Explorer 只按区块号查本地数据库。

固定配置：

```text
HISTORY_START_BLOCK = 22630960
MAX_BLOCKS_PER_QUERY = 1000
```

Dune API Key 从 `.env` 中自动发现：`DUNE_API1`、`DUNE_API2`、`DUNE_API3` ……。实现不写死 key 数量，后续增加编号变量即自动增加 worker。空值和重复值忽略；日志只输出环境变量名，永远不输出密钥内容。

除“每小时执行一次”这个调度周期外，数据存储、同步边界、Dune SQL 和前端查询都只使用 `block_number`，不使用真实时间。

## 本地数据库

使用 Python 自带的 SQLite：

```text
data_base/arbitrage_txs/arbitrage.sqlite3
```

`arbitrage_transactions` 表只保存：

| 字段 | 用途 |
| --- | --- |
| `tx_hash` | 交易哈希，统一小写，作为主键 |
| `block_number` | 交易所在区块 |

在 `block_number` 上建索引。不保存 `block_time`、`synced_at` 或链名。

并行同步允许 chunk 乱序完成，因此不再使用单一 `pending_next_end_block`，改为三张状态表：

### `sync_state`

- `initial_sync_complete`：首次历史同步是否完成。

### `sync_runs`

- `run_id`：本地自增 ID。
- `kind`：`initial` 或 `incremental`。
- `start_block` / `end_block`：该次任务的固定区块边界。
- `status`：`pending` / `running` / `completed` / `failed`。
- `total_chunks` / `completed_chunks`：总 chunk 数和已完成数。

### `sync_chunks`

- `run_id`、`chunk_start`、`chunk_end`：唯一确定一个 chunk。
- `status`：`pending` / `running` / `completed` / `failed`。
- `attempts`：已尝试次数。
- `execution_id`：最近一次 Dune execution，用于排查。
- `api_slot`：使用的环境变量名，如 `DUNE_API2`，不保存 key 内容。
- `result_count`：该 chunk 返回的 arbitrage 数量。

所有状态字段只描述区块任务，不保存真实时间。

SQLite 开启 WAL 和 `busy_timeout`。每个 chunk 的 arbitrage UPSERT、chunk 完成状态和 run 计数更新放在同一个短事务中。数据库主文件、`-wal`、`-shm` 和同步锁文件加入 `.gitignore`。

## Chunk 拆分规则

每次 Dune execution 最多查询 1000 个区块。区块范围是包含两端的闭区间，因此每个 chunk 必须满足：

```text
chunk_end - chunk_start + 1 <= 1000
```

在创建 sync run 时一次性生成全部 chunk，从新区块向旧区块排列：

```text
chunk_end = run_end_block
chunk_start = max(run_start_block, chunk_end - 999)
下一个 chunk_end = chunk_start - 1
```

例如 `[24136053, 24138500]` 拆成：

```text
[24137501, 24138500]  # 1000 blocks
[24136501, 24137500]  # 1000 blocks
[24136053, 24136500]  # 448 blocks
```

各 chunk 之间不重叠、不留空缺。它们可以由不同 Dune API worker 并行查询，但不能由 worker 直接写 SQLite。

## 多 Dune API 并行策略

### 角色分工

- 一个 coordinator：创建 sync run、生成 chunk 清单、调度 worker，并作为唯一 SQLite writer。
- N 个 Dune worker：N 等于可用且去重后的 `DUNE_API{n}` 数量。
- 每个 worker 固定绑定一个 API key，同一 key 同时最多只有一个 execution、轮询或 results 下载流程。

### 调度流程

1. Coordinator 从 `sync_chunks` 取出 `pending` chunk，默认按 `chunk_end DESC` 放入内存待调度队列，优先同步新区块。
2. 每个 worker 有一个容量为 1 的任务队列。Coordinator 只向空闲 worker 分配一个 chunk，并在分配时先把该 chunk 标成 `running`；较快的 key 完成后立即获得下一个 chunk，不需要等待其他 key。
3. Worker 只执行 Dune HTTP 请求、状态轮询、results 分页和结果校验。
4. Worker 将完整 `ChunkResult` 放入有界结果队列，内容包含 chunk 边界、交易列表、execution ID、API slot 和错误。
5. Coordinator 从结果队列取数据，串行开启 SQLite 短事务：UPSERT arbitrage、标记 chunk completed，增加 run 的 `completed_chunks`。
6. 只有当 run 的所有 chunk 都是 `completed` 时，才将 run 标记为 `completed`；首次 run 同时设置 `initial_sync_complete=true`。

结果队列大小不超过 worker 数量的两倍，防止 SQLite 写入短暂变慢时过多 chunk 结果堆在内存中。

### 避免读写冲突

- Dune worker 不持有 SQLite 写连接，不执行 INSERT/UPDATE/DELETE。
- Coordinator 是唯一 writer，所有 chunk 即使乱序返回，也一个事务接一个事务地串行提交。
- FastAPI 查询使用独立只读连接；WAL 允许查询与短写事务并行。
- `tx_hash` 主键和 UPSERT 保证重试 chunk 不会产生重复记录。
- 临时脚本和 FastAPI 后端在启动同步 coordinator 前，必须先获取 `data_base/arbitrage_txs/sync.lock` 的操作系统文件锁。没拿到锁的进程不发起 Dune 请求。进程退出或崩溃时锁由操作系统自动释放，不依赖时间过期。

### 异常和降级

- HTTP 429：只让当前 API worker 退避，其他 worker 继续。
- 401/403 或 key 无效：禁用该 worker，将它的 chunk 重新放回队列，不记录 key 内容。
- 普通网络或 Dune execution 失败：在该 chunk 的 `attempts` 范围内重试，也可由另一个健康 worker 接管。
- 所有 key 都不可用：停止当前 run，保留 completed/pending chunk 状态，不改动已有 arbitrage 数据。
- 如果多个 key 实际共享同一 Dune 账户限额，并行不一定提升速度；可通过 `DUNE_MAX_WORKERS` 小于 key 数量来主动限制并发，默认值为可用 key 数量。

## 旧历史补录工具

固定历史区间的补录入口为：

```text
backend/labels/dune/historical_backfill.py
```

该文件只负责向现有 Dune 索引补录更早历史，不被 FastAPI 导入，也不随后端启动自动执行。它调用正式的 `labels/dune/sync.py`、`labels/dune/store.py` 和 `labels/coordinator.py`，不重复实现 Dune 请求、chunk 拆分或 SQLite 写入逻辑。

手动运行：

```bash
cd backend
uv run python -m labels.dune.historical_backfill
```

脚本流程：

1. 获取 `sync.lock`，创建或打开 SQLite，读取 `sync_state` 和未完成的 initial run。
2. 原始 initial run 已完成区间 `[24136053, 25641145]`。当前脚本补充其前一段等长历史区间 `[22630960, 24136052]`，并一次性写入全部 chunk 边界。
3. 如果存在未完成 run，保留 completed chunk，将上次进程遗留的 running chunk 恢复为 pending。
4. 发现并校验 `DUNE_API1`、`DUNE_API2` 等 key，启动对应数量的 Dune worker 和一个 coordinator/writer。
5. Worker 并行执行 pending chunk，coordinator 串行写入结果和 chunk 状态。
6. 所有 chunk 成功后，将 run 和 `initial_sync_complete` 标记为 completed。

脚本每完成或失败一个 chunk，立即刷新输出以下进度：

- 当前 chunk 序号和 chunk 总数。
- 当前 `[StartBlock, EndBlock]` 范围。
- 已覆盖区块数、总区块数和完成百分比。
- 当前 chunk 返回的 arbitrage 数量和数据库累计数量。
- Dune `execution_id`、`api_slot`、轮询状态、重试次数和错误原因。
- pending/running/completed/failed chunk 数量，方便定位断点。

进度百分比只根据区块数计算，不使用真实时间。

补充脚本使用固定区块范围，不再查询链头；仍校验 `chain_id=1`。正常后端增量同步获取链头时，如果主网 RPC 错误返回创世区块，则从已知主网区块开始只按区块号向上探测并二分查找最高可读取区块，不根据时间估算区块号。

如果脚本中断，再次运行同一文件时只重排未完成 chunk，不重新查 completed chunk。该脚本作为显式维护工具保留，不参与正常增量同步。

调试期间不要同时运行临时脚本和后端同步器。操作系统文件锁作为强制保护，防止两个 coordinator 同时调用 Dune 或写 SQLite。

## 后端启动行为

1. FastAPI 启动时初始化 SQLite，然后读取 `initial_sync_complete`。
2. 如果值为 `false`，后端不自动执行大规模历史回填，只记录历史数据尚未准备完成。
3. 此时后端 API 可以读取 SQLite 中已有的部分数据，但必须向前端标明“首次同步未完成”，不能将未覆盖区块解释为没有 arbitrage。
4. 如果 `initial_sync_complete=true`，后端启动后只从本地 `MAX(block_number)` 向当前链头做增量同步，然后每小时更新一次。
5. 如果后端上次的 incremental run 中断，启动时先重排该 run 的未完成 chunk。
6. 只有拿到 `sync.lock` 的 FastAPI worker 会启动 coordinator；其他 FastAPI worker 只提供查询 API。

这样，大规模首次同步可以单独观察和排查；正常启动后端时通常只需补很少的新区块，不会把后端启动时间和首次回填混在一起。

## 每小时增量同步

1. 只有 `initial_sync_complete=true` 时才执行增量同步。如果存在未完成的 incremental run，先重排它的未完成 chunk，不创建新 run。
2. 否则，从 SQLite 读取 `MAX(block_number)` 作为 run `start_block`，读取当前 Ethereum 最新区块作为 run `end_block`。
3. 一次性生成该 run 的全部 chunk，`start_block` 包含在最后一个 chunk 中。
4. 使用当前可用的多 Dune API worker 并行查询 chunk，coordinator 串行写入 SQLite。
5. 全部 chunk 完成后将 run 标记为 completed。

正常增量同步不保存“已经检查到的最新区块”游标。每个新任务的起点仍然是本地已发现的最新 arbitrage 区块。

如果 Dune 暂时还没计算出近期区块的 arbitrage，本地 `MAX(block_number)` 不会前移，下一小时会再查同一段新区块。

同一时间只允许一个同步任务。前端不再触发 Dune refresh。

## Dune 远端 SQL

Dune Query Editor 建立两个 Number 参数：

- `StartBlock`
- `EndBlock`

```sql
SELECT DISTINCT
    tx_hash,
    block_number
FROM dex.atomic_arbitrages
WHERE blockchain = 'ethereum'
  AND block_number >= {{StartBlock}}
  AND block_number <= {{EndBlock}}
ORDER BY block_number DESC, tx_hash DESC
```

SQL 不查询 `block_time`，也不使用 `LIMIT 500`。每次 execution 传入的 `StartBlock` 和 `EndBlock` 最多覆盖 1000 个区块。后端仍根据 Dune 返回的 `next_offset` / `next_uri` 取完该 chunk 的所有结果页。

单个 chunk 的执行请求示例：

```json
{
  "query_parameters": {
    "StartBlock": 24137501,
    "EndBlock": 24138500
  }
}
```

查询保存在公开 Dune 地址：[Query 8200562](https://dune.com/queries/8200562)。

## 后端 API

新增本地查询接口：

```http
GET /api/arbitrage-transactions?from_block=24136053&to_block=24136232
```

响应包含 `tx_hash`、`block_number`、固定的 `history_start_block=22630960`、当前本地最大 arbitrage 区块号、`initial_sync_complete` 和当前请求区块范围的 `coverage_complete`。

`coverage_complete` 通过 `sync_chunks` 判断：如果该页范围覆盖的所有首次 chunk 均已 completed，才返回 true。这样即使 chunk 并行乱序完成，前端也不会把未同步的页面解释成“没有 arbitrage”。

API 只查 SQLite，不等待 Dune，并校验 `from_block <= to_block` 和查询范围大小。

现有 `/api/arbitrage-hashes/refresh` 不再由前端调用。

## 前端改动

1. 删除 `App.vue` 中的全量 hash 缓存和 Dune refresh 逻辑。
2. `BlockPanel.vue` 每次加载区块页后，用该页的最小和最大区块号查本地 API。
3. 根据返回的 `block_number` 给区块画红框。
4. 进入单区块的交易视图后，根据小写后的 `tx_hash` 给 arbitrage 交易画红框。
5. 最新区块页可以继续每 12 秒刷新，但只查本地 SQLite，不触发 Dune。
6. 区块 `22630960` 之前显示“无 arbitrage 数据覆盖”，不显示成“没有 arbitrage”。
7. 红框说明为“Dune atomic arbitrage 记录”，与本地 `arbitrage.json` 检测结果区分。

## 失败处理

- Dune 查询或分页读取失败：已完成 chunk 保留，当前 chunk 重新入队或标记 failed，不改动 arbitrage 表。
- HTTP 429 或临时网络错误：按 API worker 分别退避，不阻塞所有 worker。
- 结果中存在非法 hash 或区块号：当前 chunk 整体不写入、不标记 completed。
- 进程中断：重启后将遗留的 running chunk 恢复为 pending，只重试未 completed chunk。
- 多进程启动：操作系统文件锁确保只有一个 coordinator，SQLite 只有该 coordinator 内的单 writer 写入。

## 验证

- 首次临时脚本能分 chunk 写入从 `24136053` 到固定链头的所有 Dune 结果。
- 临时脚本可以独立执行、实时输出区块进度，中断后重启能从失败 chunk 继续。
- `initial_sync_complete=false` 时启动后端不会自动跑历史回填；完成后启动后端只做增量同步。
- 临时脚本与后端复用同一套 Dune、chunk 和 SQLite 实现，没有重复同步逻辑。
- 环境中有 2 个唯一 key 时最多并行 2 个 chunk；后续增加 `DUNE_API3` 时无需改代码即可增加 worker。
- 同一 API key 不会同时执行两个 chunk，不同 key 不会领取同一 chunk。
- chunk 乱序返回时只有 coordinator 写 SQLite，没有 `database is locked` 写冲突，run 完成计数正确。
- 任意 worker 遇到 429 或无效 key 时，其他 worker 可继续，失败 chunk 不会丢失。
- 进程在多个 running chunk 时中断，重启后只重排未 completed chunk。
- 查询 1000 个区块时只生成一个 chunk；查询 1001 个区块时生成两个 chunk。
- 多个 chunk 之间没有重叠和缺口，每个 chunk 最多 1000 个区块。
- 首次同步和增量同步在中间 chunk 失败后，都能从失败 chunk 续传且不跳过区块。
- 没有新 arbitrage 时，下一个新任务的 `StartBlock` 保持不变。
- 发现新 arbitrage 后，下一个新任务的 `StartBlock` 是本地最大 arbitrage 区块号。
- 同一区块多笔 arbitrage 不会遗漏或重复。
- Dune 单个 chunk 的多页结果能全部取回。
- 前端历史翻页时，红框来自当前区块范围的 SQLite 查询。
- 前端不再调用 Dune refresh API。
- 后端测试、TypeScript 检查和 Vite build 通过。
